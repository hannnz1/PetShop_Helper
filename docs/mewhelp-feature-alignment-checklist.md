## 2. 为什么会缺功能：从手册到 spec，再到 plan 和代码

### 2.1 已批准的范围比参考项目完整界面小

第 9 章第一部分 spec 的“按意图的 token 账”明确只要求 **CLI 报表及只读 API**；没有要求 `/observability` 页面、后台作业按钮、三张报告总览和读图说明。手册提到多信号 evidence_confidence 与评估集校准，但当前第一部分 spec 没有给校准安排独立任务；第二部分 spec 保留旧入口、拒绝随意新增 0.5 阈值，也没有补入校准任务。

第 9 章第二部分 spec 的“方案选择”明确采用 **受保护的审核 API/CLI**，记录了用户选择；“非目标”还写明“本次先交付反馈 API”。因此缺审核页面属于当时范围选择，在新目标下需要补充，不能说既有计划实现漏了整套审核逻辑。

证据：[ch09 观测 spec](superpowers/specs/2026-09-27-ch09-observability-evaluation-design.md)、[ch09 飞轮 spec](superpowers/specs/2026-09-27-ch09-knowledge-flywheel-design.md)、原手册 `C:/Users/Administrator/Documents/PetShop_Helper开发文档/9/理论学习：可观测性与数据飞轮.md`。

### 2.2 部分需求在 plan 中被缩小或没有形成可执行任务

第 10 章 spec 说明分类用于问题池主题聚合，但没有定义逐题分类表、查询接口、分页、重跑幂等和后台页面。plan 的 Task 6 标题是 **Light serving, held-out evaluation and pool report**，明确只定义 pool category report。实现 `classify_pool.py` 也只生成计数 JSON；所以“有分类脚本”不等于 MewHelp 的“分类入库→分布→按主题看问题”闭环。

原 `10.md` 明确包含 LLM 修错别字；当前 spec 在权限段提到“修错”，却没有定义这一阶段的输入、输出和评估；plan 没有专门的修错任务；代码实际跳过。训练增强写进了 spec / plan，并实现 `augment_fn` 扩展点，但 CLI 没有接模型增强，这一项是实现交付未闭合，不能只归因为缺额度。

评估计划只定义 micro/macro/per-class F1，因此没有覆盖参考项目的 P/R、每类混淆矩阵和逐条错误诊断；验收 dashboard 与 `/healthz` 也未形成任务。

证据：[ch10 spec](superpowers/specs/2026-09-27-ch10-topic-classifier-design.md)、[ch10 plan Task 3/6](superpowers/plans/2026-09-27-ch10-topic-classifier-plan.md)、原手册 `C:/Users/Administrator/Documents/PetShop_Helper开发文档/10.md`。

### 2.3 跨章接口没有被最终端到端验收接起来

第 4 章 plan 明确把 👍/👎 做成“纯前端交互、不落库”，把入池推迟到后续飞轮章。第 9 章补了后端 `/api/feedback/unresolved`，但聊天页 `addFeedback` 仍只禁用按钮并显示“已反馈”，没有发 HTTP 请求。各自任务可通过局部检查，组合起来却没有采集到用户反馈。这是跨章接线及验收遗漏，应补前端真实请求和浏览器到数据库的证据。

证据：[ch04 plan 反馈任务](superpowers/plans/2026-09-26-ch04-hybrid-rag-source-plan.md)、[聊天页](../app/static/index.html)、[反馈 API](../app/api/flywheel.py)。

### 2.4 离线阶段完成被容易误读成整章完成

第 10 章 spec 的“验收与阶段状态”允许先完成离线代码，但完整通过另需真实数据、训练、留出集指标、ONNX 全量一致性和真实服务。验收记录为 46 项相关测试通过、合成原始样例 30 条；加补充后 train=62/val=1/test=1，训练 `pending_data`、导出 `pending_compute`。这不是有效模型质量证明。

第 4 章已留痕 300 题、1200 条策略记录，474 条成功生成、726 条调用错误，最终 `partial`；第 9 章向量回流和真实标准化也有待验收项。模型余额、服务和算力问题可以解释真实验收暂停，不能解释反馈未接线、缺数据库分类闭环或缺页面。

证据：[ch04 留痕](../dev-notes/ch04.md)、[ch09 飞轮验收](ch09-flywheel-acceptance.md)、[ch10 验收](ch10-topic-classifier-acceptance.md)。上述是已有记录，本次没有探活确认服务是否仍处于相同状态。

### 2.5 没有持续维护“手册→参考功能→spec→任务→验收证据”的总表

实现按章节任务推进，缺少跨章总体验收；部分 spec 仍写“待用户审阅”，计划保留未勾选项，而 dev-notes 已记录实施及阶段 finish，进度口径不能只靠一个文件判断。第 4 章源 spec 还保留早期 80 题描述，后续实际范围已扩到 300 题。最新代码在 worktree、主目录较旧，又进一步放大了“看起来没有开发”的问题。

从记录能确认的是范围选择、任务缺口和状态不同步，不能推断每次遗漏的主观原因。开发执行方应对需求映射、跨章接线与交付口径负责；不能把这些缺口全部归因于用户未充值或未配置环境。本清单作为总表起点，后续每项必须挂补充 spec / plan 和验收证据。

## 3. 已有能力与需要保留的架构差异

- 已有纯对话 SSE、结构化提取、工具调用、知识入库、混合检索及引用、LangGraph 分流/有界工具循环、退款中断确认、三层上下文、工具注册/MCP、审核 API/CLI、观测数据接口、分类器离线代码。缺口补齐不意味着重写 1–10 章。
- 当前应用工厂/lifespan 管理资源，参考项目较多使用模块级全局；保留当前结构。
- 当前意图 usage 由 MySQL 去重汇总，参考成本脚本主要读 Langfuse Metrics API；允许不同存储路径，但报告必须说明来源与统计口径，不能混加两份用量。
- 当前人工批准与向量化分离，参考审核入口串联入库/向量化。保留可恢复的分步设计，但把状态和重试入口交付完整；“批准成功”不等于“可检索”。
- 订单、物流等演示数据和退款申请流程不等于支付系统真实退款；参考标准没有要求的真实支付、生产登录、多租户和真人客服平台不自动扩入。
- 参考 `model_guard.py` 目前只接在 `scripts/eval_ch04.py`，并非实时聊天机械闸。先对齐评估行为；如要实时拦截，另写设计，处理 SSE 已输出内容不可撤回的问题。

## 4. 清单使用规则

状态分为：**新增**（当前没覆盖）、**补接线**（组件已有但主流程未连接）、**待验收**（实现已有，真实结果不足）、**交付整合**（入口/文档/运行方式未统一）。以下所有复选框均未完成；描述已有基础不代表对齐项已通过。

优先级 P0 为运行基线/数据真实闭环，P1 为质量和运营可操作性，P2 为教学与解释性展示。只补代码仍不能把待验收项勾上。

验收证据至少含：基线提交、命令/浏览器操作、输入集或数据版本、实际输出、失败/跳过项与报告路径。收费调用先确认已有授权覆盖的数据与范围；小样本冒烟通过后再跑大批，保持成功缓存，失败项单独续跑。新库/框架接口动手前按用户要求通过 Context7 官方文档核对锁定版本。聊天页面按用户例外走 Vibe Coding，后端走 Superpowers；数据/Prompt 以标注集评估替代 TDD。
