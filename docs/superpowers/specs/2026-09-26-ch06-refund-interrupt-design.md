# PetShop_Helper 第 6 章设计：指代消解、选单中断与退款申请

> 状态：待用户书面评审。依据：`C:/Users/Administrator/Documents/PetShop_Helper开发文档/6.md`、已批准的第 5 章设计，以及本轮用户选定的样例订单架构。第 4/5 章真实上游验收仍为 `pending_upstream`，本章不自动调用余额不足的 glm 上游。

## 目标与边界

把第 5 章透传的 `coref` 变成短历史指代消解；把“退款退货”和“售后”意图接入确定性的退款子流程。缺少或报错订单号时，图暂停并给出该用户的样例订单；点选后从同一会话检查点恢复。订单归属与退款政策证据通过后，模型最多提出退款申请入口，真正写入只在用户确认固定原因表单后由独立 HTTP 动作完成。无真实订单服务、支付退款或自动审批；申请状态只表示“待人工审核”。

用户已选择 MySQL 持久样例订单与独立退款申请表。样例数据须显著标注为演示数据、使用固定演示用户，在独立迁移/种子脚本中显式导入，不以现有第 2 章按订单号伪造的随机订单数据证明归属。现有 `user_id` 是客户端传入的演示身份；正式身份认证不在本章范围。

## 对话图与数据流

```text
START → resolve_reference → classify_intent
  ├ 退款退货/售后 → fetch_order ──interrupt(select_order)──→ resume
  │                         ↓ 已校验本人订单
  │                  retrieve_policy → 证据闸
  │                         ├ 弱 → 明确拒答/低置信记录 → log → END
  │                         └ 强 → 有界 agent_llm ↔ agent_tools
  │                                     ↓ 可提出 refund_form
  │                                  final_answer → log → END
  └ 其余 → 沿用第 5 章出口
```

`resolve_reference` 以本轮前最近 6 轮完整消息为上下文，用 LangChain Prompt 链把“那它呢”等半句补为检索/分类可用问题，完整问题应保持原意。模型异常、空答或超预算时返回原话。原始 `query` 和 MySQL 审计消息保持用户原文，新增 `resolved_query` 仅供意图、订单号抽取和检索使用；不能根据历史编造新订单号。第 7 章摘要边界尚不存在，本章只做滑窗。

`fetch_order` 从消解后的话中抽取 4 位以上连续数字，使用数字前后 lookaround 兼容“订单1001”。无号或订单不属于当前用户时，先只读列出该用户样例订单，再调用 `interrupt({type: "select_order", orders: ...})`。用户点选的 `order_id` 也重新校验归属；错误点选继续暂停，不显示他人订单。`interrupt` 前只有只读操作，保证节点重跑安全。用户没有样例订单时返回可解释的兜底信息，不进入无限选单中断。

`retrieve_policy` 将原诉求和样例订单状态组合为检索种子，最多扩写为 3 条查询，异常或空结果回退原查询。沿用第 4/5 章的 hybrid-rerank 检索与编号证据约束，按 chunk ID 去重并保留最高分；未通过充分性检查就拒答，不生成退款入口。模型只能基于本人订单快照与已核验政策作解释，不宣称已退款或保证通过审核。

## 写入边界与数据

`submit_refund` 作为模型可见的“建议提交入口”工具，不承担写库。图在拦截该调用时再校验本人订单、政策证据和本轮订单 ID，返回 `refund_form` 建议动作；失配则不给表单并提供本人订单选择入口。工具函数自身也校验归属，防止未来接入执行分发层时失守。模型最终答复只说可填写申请，不能说已办理退款。

`sample_orders` 至少保存订单号、演示用户 ID、状态、商品、金额；`refund_requests` 保存申请号、会话 ID、用户 ID、订单号、固定原因、状态、`request_id`、创建时间。`request_id` 唯一；同标识同内容重试返回原申请号，同标识不同内容返回 409。提交 API 重新查会话和订单归属，不信任前端表单或模型草稿；原因只接受“七天无理由、质量问题、发错货、不想要了、其他”。该 API 只创建待人工审核申请，不改订单状态，也不碰第 5 章工单或转人工状态。迁移不得清空已有表。

## 续跑与接口

`POST /api/actions/resume` 接收演示 `user_id`、`conversation_id` 和所选 `order_id`，核实会话归属后查看 SQLite 检查点确实在 `select_order` 中断，才以 `Command(resume=order_id)` 续跑。沿用 `/api/chat` 的 SSE 帧，增加 `interrupt` 帧，其中带 `kind=select_order`、`conversation_id` 和本人订单列表；发生中断时不发 `done`。非中断、其他中断类型、忙碌会话、越权会话分别明确拒绝，不把普通新消息当续跑。执行前仍校验 MySQL 审计标记；允许合法的待选单检查点，不放开第 5 章对异常 pending 节点的保护。

`POST /api/actions/create-refund` 接收会话、订单、固定原因及唯一 `request_id`，返回申请号与“待人工审核”。表单必须由用户显式确认后发送；取消不写库。聊天页按既有 Vibe Coding 约定直接迭代选单和退款卡片，共用 SSE 解析，不对页面套 brainstorm/TDD/code review。
