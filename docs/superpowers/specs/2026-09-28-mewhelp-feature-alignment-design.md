# PetShop_Helper：MewHelp 功能对齐补充设计

日期：2026-09-28。状态：**用户已批准补充 spec，并回复“批准实施计划”；[实施计划](../plans/2026-09-28-mewhelp-alignment-plan.md)进入连续实施。**

## 1. 目标与开发基线

用户原话：“请按照这个MewHelp 功能对齐清单，更新我peshophelper的功能”。依据为 [21 项功能对齐清单](../../mewhelp-feature-alignment-checklist.md)，本设计承接其全部范围与验收标准。用户无需重新选择技术栈或重新确认已存在的业务流程。

成功标准分为两层：21 项均有可操作、可追溯的等效功能；第 1–10 章真实验收在本项目最终代码、数据和模型上通过。假模型测试、参考历史报告和缺模型时的 pending 不作为真实达标证据。

使用现有 `PetShop_Helper/.worktrees/ch08-tool-system`，基线 `abe481e`，继续保留 `feat/ch09-observability` 的已有工作。主目录仍为较早版本，实施期间所有命令明确使用 worktree 绝对路径；集成时保留两侧未提交文件与本地配置，先比较再选择快进/合并方式，不覆盖用户 `.env`。最终 README 和启动命令必须指向交付版本。

## 2. 方案与边界

选择**在现有模块上补接口和运营闭环**。直接整体复制 MewHelp 会覆盖现有审核保护、数据血缘和 Windows 适配；另建第二套后端会重复状态与配置。本方案复用应用工厂、MySQL 仓储、LangGraph、JobRunner、审核服务和轻量分类服务，新增必要的模块与页面。

固定保留 Python/FastAPI/LangChain/LangGraph/MySQL/Milvus/Langfuse，以及配置化 OpenAI 协议上游；不更换指定模型或外部服务。客服实时路径不引入第 10 章批量分类。支付退款、生产登录、多租户和真人客服平台不扩入本次。

工作分为四个独立交付批次，实施计划按批展开，共用本设计的接口与完成标准：

| 批次 | 清单项 | 主要产出 |
|---|---|---|
| I 基线与检索/反馈 | A01、A02、F01、R01–R03 | 最新运行入口、真实反馈接线、检索校准与评估型号校验 |
| II 运营后台 | O01–O03、W01、W02 | 观测/审核页面、受保护作业、回流状态与完整操作链 |
| III 分类闭环 | C01–C06 | 语料与增强补全、诊断报告、分类落库、主题和验收后台 |
| IV 真实验收与交付 | R04、C07、D01、D02，以及 W02 真实部分 | 真实报告、最终逐章复验、部署与演示说明 |

## 3. 批次 I：基线、反馈与检索质量

### 3.1 运行基线和状态

在 README / 部署文档给出主服务、MySQL、Milvus、MCP、Langfuse、8110 分类器的启动依赖与检查入口。存在性检查不打印密钥；健康检查不自动清库、重建卷或发起付费请求。配置缺失明确列出变量名，使用现有环境加载规则。核对 spec/plan 与 dev-notes，更新可证实的状态；没有批准证据时保留待审，不补造历史。

清单每项记录实现状态、验收状态、提交/报告和阻塞条件，区分 `implemented`、`verified_offline`、`verified_live`、`pending_*`；已有 `passed/partial/failed` 报告语义不强行替换，汇总层明确映射。

### 3.2 回答消息标识与反馈

后端持久化本轮可见 assistant 消息后，返回其真实 MySQL ID。Graph 正常结束和中断恢复后的完成出口在 SSE `done` 帧增加可选 `assistant_message_id`；只完成动作预览/选单中断而未保存最终答案时不提供可反馈 ID。扩展字段向后兼容。历史接口已经返回消息 ID，直接绑定各条历史气泡。

聊天页只对已经持久化的答案开放 👎，调用现有 `POST /api/feedback/unresolved`，使用该气泡所属用户、会话和消息 ID，不使用点击瞬间可能已切换的全局会话。成功后锁定；网络失败展示重试；服务端沿用消息归属检查和 `source_ref` 唯一约束。禁止用“本会话最新一条消息”推测刚才的答案 ID。

👍 维持轻量本地评价并明确标为本地状态；不冒充已送达后台。此行为符合清单允许的等效方案，不新增无实际用途的正反馈表。

验收覆盖新回答、恢复历史、切换会话、流中断、错误归属、重复请求，以及浏览器点 👎 后数据库实际新增正确原问句。聊天页面按用户指定 Vibe Coding；消息 ID 与仓储行为走后端回归。

### 3.3 多信号置信度和校准

新增独立纯计算模块，按参考四信号和固定权重计算：Top-1 精排分 0.5、有效证据数 0.2、Top-1/Top-2 差距 0.2、Top-3 关键条款命中 0.1；有效证据线 0.3，数量封顶 3。信号输入仅来自 reranker，不能把 Milvus dense/BM25/RRF 分数混入同一尺度。异常非有限分数拒绝作为有效证据，空列表得 0。

Graph 强制知识路径使用校准过的证据置信度决定是否继续语义自检，低置信拒答并入池；trace 保存各信号及所用阈值版本。工具路径继续保留明确的 Top-1 闸与语义自检，并在报告中注明规则，不无意改变退款政策路径。

校准 CLI 使用固定标注集和检索结果，扫描 0.05–0.95、步长 0.01，以可答通过率减库外放行率（Youden J）选阈值，严格更优才更新，平分保留先到的小阈值。保存数据集 hash、策略、信号版本、扫描表、推荐值及样本数。实际启用读取与当前配置匹配的校准结果；没有有效校准时维持旧闸并显示 pending_calibration，不能照抄参考 0.26。

### 3.4 分类回退与型号机械校验

query_faq 的可选语义 category 过滤为空或全弱时最多撤销该分类过滤重试一次；其它权限/归属约束保持。两次均弱继续现有拒答路径。记录是否回退，不增加聊天模型调用。

型号机械校验先接第 4 章评估生成：抽取 `MH-字母数字` 形式的型号，与本题 evidence 中原样型号逐字比对；无依据则最多修复一次。原答案、异常型号、修复后答案和校验状态留在报告，修复后再执行相关质量评估。仍有异常不能判型号校验通过。实时 SSE 输出后的自动撤回答案不在参考已有功能内，不纳入本次。

## 4. 批次 II：运营后台与知识回流

### 4.1 访问与后台作业

页面外壳可加载，受保护数据和操作沿用管理员 Bearer。审核/主题数据使用 `KNOWLEDGE_REVIEW_TOKEN`；观测/验收报告使用 `OBSERVABILITY_ADMIN_TOKEN`。管理员在本机页面输入凭据，只在页面内存保留；不写 URL、静态文件或浏览器持久存储。

新增作业在统一 JobRunner 白名单注册，并在所有启动、停止、状态、日志入口按作业类别强制鉴权；旧 `/api/jobs` 不能成为新敏感作业的旁路。作业参数是有限的结构化字段，不拼接任意 shell。成本较高的重跑需显示范围并确认，外发权限检查仍由作业端执行。纯读页面不自动调用模型。

### 4.2 审核与发布状态

`/review` 消费现有 `/api/review/questions`、decision、publish API；补充详情和状态字段，复用服务逻辑。显示标准问题、频次、遮蔽后的原始问句、建议答案、正式答案、来源和操作审计。

人工可 reject/defer/merge/approve；批准须填正式答案及知识类别。发布后展示 `approved_pending_vector`，并根据关联知识行的真实向量状态展示可检索/失败。补向量使用现有幂等作业，页面可发起重试，但嵌入失败不丢失核准决定。只有向量写成功才显示可检索。

W02 用隔离问题池演示三入口→标准化归并→审核→发布→向量化→下一轮命中。真实语义准确性与假模型事务验证分开出报告；真实文本外发沿用已有独立授权边界。

### 4.3 观测总览和报告

`/observability` 包含意图用量、评估趋势、置信度校准三块。新增 overview 组装接口复用现有 usage/eval-trend 仓储与校准报告，不在前端重算权威指标。每块单独提供 ready/missing/pending/error；一项依赖失败不阻断其它区块。

意图账增加总量、调用数、均值、占比、时间范围、usage 缺失数量；按实际可用 usage 汇总，缺失不当零。实际用量仍以当前 MySQL 账为主，通过 request/run ID 和 Langfuse 对账并记录差异口径，不将两边相加。没有价目表不展示货币金额。

趋势保留数据集 hash、策略及分母可比性；旧指标不可假冒本轮。校准页面展示推荐与生效值及版本一致性。读图小注默认由确定性模板从本报告生成，缺数字就明确缺失；可选模型小注开关默认关闭，生成后校验数字、绑定 run ID，失败回退模板，不增加客服请求成本。

## 5. 批次 III：语料、分类落库和验收后台

### 5.1 语料修错与增强

语料在本地遮蔽和去重后进入修错模型，只改错字/乱格式，不增删诉求、不改商品型号；再次去重后预标。保存来源 ID、脱敏原句、修正句、阶段状态及审核关联。所谓 raw 导出也必须是脱敏版本。失败保留原脱敏句并显式标失败，不能无声丢行或标“其他”。

新增标注评估样例覆盖错字、方言、多诉求、无错、型号，逐条核对语义保真；模型预标仍需黄金集 exact-set≥80%。人工审核入口、术语哈希和数据集血缘规则保持。

数据集 CLI 增加显式增强模式，调用现有 build_dataset 的增强流程。必须先固定 80/10/10 划分，再生成训练集同义变体；保存父样本 ID、模型/Prompt 版本和结果缓存，验证/测试 hash 不改变。失败不拿原句凑数。未满足权限/额度时记录 pending，不能声称增强已跑。训练数据不足每类 100 的现有闸保持。

### 5.2 分类质量报告

扩展评估输出为统一 JSON 和 Markdown：micro/macro P/R/F1、17 类 P/R/F1/support、TN/FP/FN/TP、遮蔽错误样例及漏打/多打/错位。报告记录模型、阈值、术语、测试集 hash 和运行时间。

严格类 F1≥0.9、中档≥0.8，宽档只报告；无 support 的关键类不得判通过。评估和服务继续共用阈值/空标签兜底函数。错误样例按标签位统计与矩阵对账，不能将错例条数误当 FP+FN 数。

### 5.3 分类持久化和批处理

新增 `topic_classifications`：`id`、唯一 `question_id`（外键到 low_confidence_questions）、`labels` JSON、`model_version`、`taxonomy_hash`、`threshold`、`input_hash`、`run_id`、`classified_at`。新增分类批次表保存 `run_id`、模型版本、开始/结束时间、待处理/成功/失败数、状态、报告路径；不存未遮蔽问题原文。提供独立增量 SQL 与可重跑迁移命令，先隔离库验证。

默认处理未分类问题，至少 10 条才运行，允许 `--force`；读取并遮蔽问题，调用本机分类服务，严格验证结果长度、顺序、17 类标签合法性及版本，然后按批事务落库。单进程作业互斥、数据库唯一约束兜底；并发冲突只按已存在结果恢复，不覆盖其它批次。网络调用在数据库写事务外。

同一版本重跑跳过已分类行，第二次报告 empty；升级模型不会自动改历史结果，只有明确 `--reclassify` 才更新并记录旧/新版本摘要和本次报告。默认运行不把分类器放进实时聊天路径。服务暂不可用不写空标签。

8110 `/healthz` 增加 ready、model_version、taxonomy_hash、threshold；`/classify` 保留 `results` 并增加模型版本元数据，原客户端仍可读取 results。healthz 不披露密钥、模型内部绝对路径或用户文本。

### 5.4 主题统计接口与页面

新增受保护的 `GET /api/topics/distribution` 和 `GET /api/topics/questions`。前者返回17类计数、独立问题数、未分类数、版本口径；后者按合法类名、offset/limit 返回稳定排序的分页问题、来源、分类信息和审核关联。默认统计当前保存结果，不把历史批次重复叠加；类别计数按多标签展开，独立问题数去重。

`/topics` 展示分布和零样本类，点击进入 `/topics/questions`。数据来自分类表，和 SQL 对账；默认遮蔽原始问句中的私人字段。待审核关联不存在时明确提示，不伪造审核状态。

### 5.5 分类器验收后台

新增 `/acceptance` 及数据、评估、错误详情页面，通过受保护 `/api/acceptance/*` 读取现有版本产物与分类批次；展示黄金闸、语料血缘、划分、训练模型、阈值扫描、质量红线、ONNX 一致性、服务实测、分类入库九项。

报告缺失、解析错误、版本不匹配、pending、failed 分别展示；API 不重新算 F1，不把文件存在视为通过。健康探针具有短超时，失败不影响其它报告读取。重跑入口复用受保护白名单作业；外发/训练默认需明确范围且必须通过服务端许可检查。报告和截图都标明模型与数据版本。

## 6. 批次 IV：真实验收、预算和部署

第 4 章沿用已授权的 300 题/四策略，先核对成功缓存与 Prompt/证据指纹，只补失效/失败项；不能因为“继续开发”重复计费整批。先小样本确认服务与字段正常再继续完整范围。生成/裁判错误必须为零才可称报告完整，质量不达标仍是 FAILED。

第 10 章真实用户语料外发不从第 4 章授权推导。需要时依据已有批准范围或明确取得新增授权；模型、数据与算力缺失继续推进不依赖它们的实现，但不伪造训练成绩。训练完成需本项目留出集达红线、验证阈值重演一致、全量 Torch/ONNX 标签 mismatch=0（含兜底），再验证真实 8110 和分类入库。

部署交付统一首页导航、PowerShell 单次命令、依赖检查、增量迁移、故障恢复、报告位置及逐章演示样例。已有定时评估说明复用，补分类/飞轮调度说明；不自动启用每日收费全量任务。最终完成前按清单第 6 节复验 1–10 章，并保留模拟业务来源说明。

## 7. 验证与交付纪律

- 后端按任务 TDD，重点测试消息归属/真实 ID、检索回退边界、数字口径、分类结果错位、并发唯一约束、权限和恢复行为。
- Prompt/数据步骤用人工标注评估集；聊天页面按 Vibe Coding 和实际浏览器验收，其余页面按相应模块测试/评审。
- 测试分纯离线、隔离 MySQL/Milvus、本机集成、真实模型四层，报告明确依赖和排除范围；全量验证只在阶段集成点执行，修复后先跑受影响范围。
- 每完成 brainstorm/spec、计划评审、任务、code review 或 finish，立即追记 `dev-notes/mewhelp-alignment.md`；涉及章节同时链接原章节记录。
- 每批实施末尾做独立复核；执行方式在书面 plan 审阅时选择，优先连续实施后集中复核以节省上下文开销。
- 21 项映射不得遗漏：A01/A02/F01/R01/R02/R03/R04/O01/O02/O03/W01/W02/C01/C02/C03/C04/C05/C06/C07/D01/D02。验收标准以清单各条为准，实施 plan 必须逐项列证据。

## 8. 官方接口依据及自查

本轮已用 Context7 查询 FastAPI 官方文档 `/websites/fastapi_tiangolo` 的 APIRouter dependencies/lifespan，以及 SQLAlchemy 2.0 官方文档 `/websites/sqlalchemy_en_20` 的 async_sessionmaker.begin、AsyncSession 并发边界和 MySQL upsert。

依据：[FastAPI APIRouter](https://fastapi.tiangolo.com/reference/apirouter/)、[FastAPI lifespan](https://fastapi.tiangolo.com/reference/fastapi/)、[SQLAlchemy asyncio](https://docs.sqlalchemy.org/en/20/orm/extensions/asyncio.html)、[SQLAlchemy MySQL](https://docs.sqlalchemy.org/en/20/dialects/mysql.html)。实现时继续查 LangChain/LangGraph/Langfuse/训练工具等涉及的新接口，并核对 uv.lock/已安装版本；本 spec 不以最新文档替代版本兼容验证。

自查：清单 21 项均有批次归属；反馈依赖真实消息 ID 而非 latest 查询；新作业不能走旧无鉴权入口；分类表增量不清库；校准值不照抄历史结果；数据/模型版本贯穿报告；真实验收与离线完成分开。用户已批准本 spec，下一阶段为审阅书面实施计划后执行。
