# PetShop_Helper 第 9 章第二部分设计：低置信度问题到人工审核知识回流

**状态：待用户书面评审。** 2026-09-27 brainstorm 定稿后形成。实现以当前仓库和第 9 章手册为准，不覆盖已完成的第一部分可观测性。

## 目的与验收

客服答不上来的问题不能只留下兜底回复。运营人员需要知道哪些缺口反复出现，审核后补一条可靠知识，使以后相似问题可检索。手册规定三种入口：检索证据弱、生成自检 `useful=false`、用户反馈“没解决”。现有 Graph 已将前两种写入 `low_confidence_questions`，第三种和后续审核回流尚缺。

验收以隔离 MySQL 和合成问句为主：三种入口都能留痕；两种说法可归并为一个标准问题，重复运行与重复反馈不重复计数；无效匹配 ID 不会误合并；审核人能丢弃、合并、暂缓或批准带正式答案的知识；批准只写 MySQL 待向量化记录，向量化成功后才可检索。上游模型/Milvus 缺席时明确待处理，不宣称闭环通过。

## 方案选择

选择 **MySQL 权威队列 + 离线标准化作业 + 受保护的审核 API/CLI**。对比把标准化嵌入每次聊天请求，此方案不增加客服回复延迟，也允许在模型额度不足时积累原始问题。对比纯文件人工处理，MySQL 的唯一约束和事务可支撑并发反馈、查重与可重跑审核。用户已选择“受保护的审核 API + CLI（推荐）”并批准按此设计写 spec。

## 数据流与边界

1. 保留现有 `low_confidence_questions` 原始记录。现有 `retrieval_low_conf` 与 `self_check` 入口不变；不新设未经标注集校准的 0.5 分数阈值。新增用户反馈入口，接收当前演示系统的 `user_id`、`conversation_id`、`assistant_message_id`，核对该消息是所声明会话的 assistant 消息并找出对应用户问句，写 `user_feedback` 原始记录。为该 assistant 消息的“没解决”事件保存唯一来源标识，重试返回同一记录。与现有聊天接口一样，`user_id` 目前由调用方声明；这不是生产级身份认证，未来接入真实登录时沿用其身份来源。
2. 后台单次 CLI 作业读取未处理的原始记录，先做本地文本清洗/个人信息遮蔽，再给聊天模型一组有限的现有标准问题候选。使用 Pydantic `with_structured_output` 得到标准 FAQ 问句、仅供参考的示例答案、`matched_question_id: int | null` 和理由。候选按规范化文本与字符重叠从未关闭队列中选取，不把全库原文塞入 prompt。模型返回的匹配 ID 必须在本次候选集中；否则标记待人工处理而不合并。上游不支持结构化输出、余额不足或调用失败时保留原始记录为 `pending_upstream`，不调用第二模型、不填旧结果。
3. 新增标准问题表与原始记录关联表。每个原始记录最多关联一个标准问题；出现频次从唯一关联行计数，不靠可漂移的累加字段。规范化完全相同的问题可直接确定性合并；模型的语义匹配是待审建议，运营人员可以拆分或调整。并发作业用唯一约束、事务与必要的行锁保证同一原始记录只处理一次，重复运行不创建第二份标准问题。
4. 独立 `KNOWLEDGE_REVIEW_TOKEN` 保护审核只读和写入路由；未配置时拒绝，缺失或错误 Bearer 拒绝。CLI 在本机使用同一审核服务逻辑，不通过无鉴权的旧 `/api/admin` 绕过。队列显示标准问题、来源、频次、示例答案与原始问句摘要。审核动作有 `reject`（垃圾/强时效/低频等原因）、`defer`、`merge`、`approve`；动作写只追加审计记录。批准必须由人工提交核准答案和知识分类，示例答案不能自动变成正式答案；重复批准同一版本幂等，冲突返回明确错误。
5. 批准后复用现有 `insert_manual_knowledge_report`，以核准问答生成 MySQL `knowledge_chunks` 的待向量化行，并保存关联 ID。现有知识写函数自有事务，因此先落核准决定，再通过可重试发布步骤写知识、回填关联；若回填失败，靠核准问答指纹与现有幂等入库规则恢复，不宣称跨两个事务原子提交。审核成功和 Milvus 同步分离；运营通过既有待向量化作业重试，MySQL 权威记录不因嵌入/向量库失败而丢失。只有向量化成功的知识算真正可检索；重复发布不得产生重复知识。强时效问题默认供审核人拒绝或暂缓，低频只是优先级信息而非硬编码自动删除。

## 安全、成本和失败处理

原始用户问句可能含订单号、电话等信息。只在本机 MySQL 存原文；模型处理前遮蔽明确个人信息。既有 `.env` 上游可能是外部服务，本次没有授权把真实用户原话发送给它；作业启动前检查上游地址，非本机地址且无单独授权开关时只报告 `pending_upstream`，绝不静默外发。真实批处理只在另行授权或切到本机模型后启用，合成样例可验证流程。审核列表和导出默认遮蔽原文中的个人信息，正式答案禁止包含原始订单号等私人内容。管理员 Bearer 仅存在本机环境配置，不进入日志或 trace。

模型任务与聊天主链路解耦，按批大小上限运行，失败项保留可重试状态。MySQL 写入故障使审核动作失败，不半写知识；Milvus 故障仅停在待向量化状态。人工审核决定和知识写入需要请求级幂等键及审计，避免双击或重试重复发布。

## 验证、限制和非目标

代码部分按 Superpowers TDD：先写三入口、幂等、候选 ID 伪造、并发归并、审核权限/状态转换、双写失败恢复测试，再实现。纯 Prompt 标准化用标注样例集验证问句和匹配结果，不以“模型能输出 JSON”替代准确性评估。最终用隔离 MySQL、假模型和可用的本机 Milvus/嵌入服务演示审核前后检索；若模型额度或向量服务不可用，报告具体 `pending_upstream` 阶段。

本设计不做第 10 章的 17 类主题微调分类器，不自动发布机器生成答案，不给聊天页面增加审核 UI。若要在聊天页展示“没解决”按钮，依用户规定用 Vibe Coding 单独实现，不套后端 TDD/code-review 流程；本次先交付反馈 API。
