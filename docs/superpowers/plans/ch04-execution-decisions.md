# Ch04 执行裁定（源 Spec/Plan 的适配层）

源文件：[Spec](../specs/2026-09-26-ch04-hybrid-rag-source.md)、[Plan](2026-09-26-ch04-hybrid-rag-source-plan.md)。本文件按固定选型修订可执行顺序；不替换 Milvus 原生 BM25/RRF、SiliconFlow BGE-M3/BGE reranker、MySQL 权威源和单一客服入口。各任务完成时追记 `dev-notes/ch04.md`，确定性代码红→绿→评审，Prompt/数据用标注集验证；只有聊天页面走用户指定的 Vibe Coding 例外。

1. **评估分两阶段且以最终口径交付。** Task 12–17 先建 A/B/C/D 四桶各 20 题共 80 题的基线，用临时 Recall@10 可作为阶段指标；Task 18 追加跨文档 E 桶并扩至五桶各 60 题共 300 题，最终对外报告统一 Recall@5、MRR、证据覆盖度、答案覆盖度、忠实度和拒答率。源 Spec §4/§8 及 Plan Task 12–18 的数字来自不同阶段，不把阶段性 80 题报告冒称终版验收。引用与反馈、后台页均按最终产物检查。
2. **Task 1 严格 fail-fast。** 先用现有 `.env` 的 `SILICONFLOW_API_KEY` 对官方 `POST /v1/rerank` 发三条合成文本，模型 ID 始终为 `BAAI/bge-reranker-v2-m3`；后续正式配置可用可选 `RERANK_API_KEY` 覆盖同账号密钥，但缺它不能使旧聊天/建库入口启动失败。`SecretStr` 只经 `.get_secret_value()` 取值，不输出密钥/请求头/原始向量。已实测 status 200，正确候选 Top-1 index 1；正式脚本仍须保留该回归。
3. **Milvus Standalone 版本与中文型号词先冒烟。** Task 1 首选固定 `milvusdb/milvus:v2.5.21`（满足官方 `run_analyzer` 的 2.5.11+ 门槛），与 ch03 共存的 Docker Compose 三件套还需 etcd、MinIO 和独立持久卷。使用当前锁定的 `pymilvus==3.0.2` 真连 Standalone，兼容判据是 `create_schema`/BM25 Function、建双索引、insert、`run_analyzer`、dense/BM25 单路、RRF 混合、filter、upsert、drop 隔离测试集合全部成功，不能只靠版本号猜测。若客户端与服务端不兼容，只在固定 Milvus 2.5+ 原生 BM25 方案内核对兼容 pin 并重跑第 1–3 章全套测试后提出修订；不得盲目降级。必须用 `run_analyzer` 与真实 BM25 检索测 `MH-W40`、`LP100`、`Pro`，确认 `chinese` 内置分词没有丢掉验收所需型号；若有损失，只在 Milvus 原生 BM25 内调整 analyzer 配置并记录用户固定“中文分词”的兼容实现，不能用 Python 关键词检索替代。冒烟未过则按原风险闸停问，不改正式 `knowledge` 集合。
4. **Windows 与项目配置接口。** 源 Plan 的 `docker-compose`、`seq`、`sleep`、`/dev/null`、`PYTHONPATH=.` 均为 POSIX 写法；Makefile 使用现有 `Windows_NT`/其他系统分支，Windows 下 `docker compose` 与 PowerShell 等待健康检查。所有示例导入不存在的 `app.config.settings` 必须改用 `get_settings()` 或显式传 `Settings`。所有上游地址和模型名从配置取，默认值仅按 Spec 的官方服务值；新字段采用可选默认，旧 ch01–03 配置和测试持续可启动。
5. **重建迁移不丢 MySQL 权威数据。** ch04 的目标是 Standalone 上的 `knowledge`，Lite 文件内同名旧集合保持原样；两者 URI 分离，先以另一隔离集合验证新 schema。Task 14 切换时先停正式 Web 和建库/挖掘作业，备份 `.env` 与 Lite 文件，在 Standalone 建空的新版 `knowledge`，从 MySQL **所有** `knowledge_chunks`（包括 ch03 已标 `done`）按同一 ID 全量嵌入/upsert，失败不修改旧状态；比对 MySQL ID 集、总数、Top-K 样例和 BM25 型号检索，再将配置指向 Standalone 并重启服务。切换前不删 Lite 文件，失败时恢复原 URI 并重启旧服务；切换后的新增 MySQL 行若需回退，先停止写入，再按 MySQL 权威行补写 Lite 后启用旧服务。保留备份直至新链路和全套回归通过，验证与回退步骤写入 Task 14 日志。
6. **增量改动双写，保留 ch03 不变量。** 不照搬 Task 4 整段替换 `vectorize_pending` 的示例；保留 `knowledge_write_lock()`、批量嵌入数量/维度校验、`zip(strict=True)`、Milvus upsert 后逐 ID 标 done 的恢复语义。新增 `text/section_path/content_type/category` 等字段时做回归；`flush` 是否必需及其和 MySQL done 的顺序先查 Context7/真实 Standalone，再用故障注入验证无重无漏。源 Plan 的未定义 `_batches` 不能进入代码。
7. **评审闸。** 源计划独立预审结论为不通过；本裁定和 Task 1 真实冒烟均通过后，再在仓库里落正式代码。若固定选型的关键链路在真实服务失败，停下向用户说明，不自换模型或检索方案。
